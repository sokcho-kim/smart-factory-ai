# 03. 프로젝트 완성도를 위한 보강 분석

기존 MILESTONES는 "본선까지 동작은 한다" 수준의 최소선이다. 본 문서는 **시연/AI 정확도/스토리** 세 축에서 무엇을 더 얹어야 수상권에 들 수 있는지를 정리한다.

## 1. Vision 파트 — 무엇이 부족한가

### 1-1. 데이터 다양성 부족 — 단일 도메인 학습의 함정

기존 계획:
- Casting (주조 양품/불량)
- NEU (강판 6종 결함)
- MVTec AD (다품종 이상 탐지)

문제: **3개 데이터가 도메인이 다 다르다**. 시연 때 "이 데이터로 학습했는데 저 데이터로 추론" 하면 도메인 갭이 너무 크다.

**보강안**:
- 시연용 "대표 제품" 한 종을 정해서 **그 도메인 안에서만** end-to-end로 동작하게 만든다.
  - 후보 1: **Casting 단일 도메인** — 학습은 NEU/MVTec로 augmentation, 추론은 Casting 시퀀스
  - 후보 2: **MVTec AD bottle/hazelnut** 한 종 — 양품→불량 시퀀스 만들기 가장 깔끔
- 채택: **MVTec AD `bottle` 클래스** — 양품/불량 모두 라벨 있음, 결함 유형 4가지 (broken_large, broken_small, contamination), 시연 스토리에 어울림

### 1-2. 시연 임팩트 — 단순 양품/불량 표시는 약하다

기존: 이미지 + verdict 텍스트.

**보강안 (시각화 강화)**:
- **Grad-CAM/Heatmap 오버레이** — YOLO bbox 외에 "AI가 어디를 의심했는가" 를 색칠. 심사위원이 "이거 진짜 보네" 라고 느낌.
- **신뢰도 게이지** — 0.94 같은 숫자가 아니라 게이지 바.
- **결함 누적 미니맵** — 한 제품 위에 최근 100개 제품의 결함 위치를 누적 → "여기서 결함이 반복된다" 시각적 임팩트.

### 1-3. 추론 속도 — 시연이 끊기면 다 망함

YOLO v8n 자체는 빠르지만, Streamlit이 매 프레임 추론 호출하면 UI 멈춤.

**보강안**:
- FastAPI `/inspect`를 **배치 호출** (1장이 아니라 8장씩) — 처리량 4배
- Streamlit은 별도 스레드에서 큐 폴링
- 추론 결과는 **이미지 캐시** — 같은 이미지 두 번 추론 안 함 (시연 반복 시)

### 1-4. 본선 환경 리스크

본선장에서 GPU가 없을 수도 있다 (노트북 시연 가능성).

**보강안**:
- 학습은 RTX 3060 Ti(현 환경)로, **추론용 모델은 ONNX export** → CPU에서도 30 FPS 확보
- Docker 이미지에 ONNX 런타임 미리 포함
- 시연용 노트북에서 사전 동작 테스트 (5/21)

## 2. 프로젝트 전반 — 무엇이 부족한가

### 2-1. "데이터가 알아서 쌓인다" 스토리의 증거

기획서는 "0% → 100% 자동 수집"을 KPI로 내세웠다. 시연에서 이게 보여야 한다.

**보강안**: 대시보드에 **"누적 검사 건수 카운터"** + **"수기 입력 0건"** 표기.
- "오늘 누적 1,247건 자동 기록 / 사람 입력 0건"
- 카운터가 실시간으로 올라가는 게 시각 임팩트.

### 2-2. "인과관계" 차별화의 증거

기획서는 "상관 → 인과" 를 강조하는데, 시연에서 이게 어떻게 보일지?

**보강안**: SHAP 워터폴 차트 옆에 **"단순 상관 vs SHAP 인과" 비교 패널** 1개.
- 단순 상관: 온도 0.45, 압력 0.42, 속도 0.38 (다 비슷)
- SHAP: 온도+압력 상호작용 73%, 속도 단독 5%
- → "단순 분석이라면 셋 다 의심했겠지만, 우리는 진짜 원인을 찾는다"

(지민 영역이지만 정환이 시뮬레이션 데이터 만들 때 이 메시지가 살아나도록 변수 설정해야 함)

### 2-3. "현장 도입 가능" 의 증거

기획서는 "웹캠 + 일반 PC"를 강조한다. 시연에서 보여야 한다.

**보강안**:
- 데모 시작 전 **"하드웨어 BOM" 슬라이드 30초** — 웹캠 3만원 + 노트북 + Docker.
- 가능하면 본선장에서 **노트북 웹캠으로 라이브 1장이라도 추론** (보너스 임팩트, 안 되면 스킵).

### 2-4. 비전 라벨 ↔ 조치 가이드 RAG의 결합

지민이 RAG 만들 때, **결함 유형별로 조치 텍스트가 1:1 매칭**되어야 한다.

**보강안**: 정환이 라벨 정할 때 **조치 가이드 텍스트도 같이 작성 (간단히 8줄)** → 지민이 그 텍스트를 기반으로 RAG knowledge base 구축.

```
crack (크랙):
  원인: 금형 온도 과열, 냉각 속도 불균일
  조치: 1) 금형 온도 80°C 이하 확인 2) 냉각 라인 점검 3) 5분 후 재검사

porosity (기공):
  원인: 원료 수분 과다, 사출 압력 부족
  조치: 1) 원료 건조 상태 확인 2) 사출 압력 +5% 조정 3) 가스 배출구 점검
...
```

이걸 정환이 미리 줘야 지민의 RAG가 "딱 맞는" 응답을 한다.

## 5. 결론

**기존 로드맵에 더할 것 (TL;DR)**:
1. 도메인 한 종(MVTec bottle)에 시연 집중 — 갭 제거
2. 시각화 강화 (Grad-CAM, 게이지, 누적 미니맵)
3. 통합 사전 작업 (라벨 표준, mock 데이터, 조치 텍스트)
4. CPU 추론 (ONNX) — 본선 환경 헷지
5. KPI 카운터 + "상관 vs 인과" 비교 패널 — 스토리 증거

이 다섯 가지가 빠지면 "동작은 하지만 평범한" 프로젝트가 된다.
